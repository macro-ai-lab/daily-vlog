# 스킬 설치·배포 관리

사용자 목표는 **세션에 저장소 주소와 “README를 읽고 현재 작업 폴더에 설치해줘”를 보내면 에이전트가 설치와 검증을 끝내는 것**이다. OS별 명령·Python/Git 사전 설치·탐색기 CMD 실행을 사용자에게 넘기는 것을 정상 설치 흐름으로 만들지 않는다. 실제 권한과 앱 승인 경계를 따른다. 제작 지침·개인 취향·콘티 확인을 설치 변경에 섞지 않는다.

이 스킬은 배포를 만드는 에이전트용이다. 설치 사용자가 별도 설치해야 하는 의존성이 아니다. 관리 스크립트는 Python 3 표준 라이브러리를 쓰며 제품 설치기의 Python 사전 설치 조건과 구분한다.

## 작업 시작

1. Git 상태·대상 저장소·기준 커밋과 이번 변경 범위를 확인한다. 새 프로젝트는 먼저 요청받은 제품 SKILL.md를 작성하고, [설치 계약](references/installation-contract.md)에 맞는 `distribution.json`을 만든다. `scripts/distribute.py init`은 기존 제품 기능을 바꾸지 않고 설치 부분을 마련한다. 기존 파일을 덮어쓰지 않는 초기화다.
2. macOS/Windows 네이티브와 Codex/로컬 Claude Code 네 경우를 모두 제공한다. 클라이언트는 현재 에이전트가 명시하고 운영체제는 호스트에서 확인한다. 일반 Claude 채팅·Cowork·WSL·모바일을 같은 지원으로 확대하지 않는다. 실제 실행하지 않은 조합을 검증 완료라고 하지 않는다.
3. Windows 작업은 [발생했던 실패와 회귀 기준](references/windows-history.md)을 읽는다. 계정·소유자 이름에 따른 선제 거부를 다시 추가하지 않는다. 실제 파일 생성·쓰기·잠금 결과를 판단한다.

## 구현과 공통 변경

기본 설치기는 `assets/install*.in`에서 `scripts/distribute.py sync --repo REPO`로 생성한다. 프로젝트별 이름·개인 지침·선택적 런타임 설정은 manifest에 둔다. 공통 템플릿을 제품마다 손으로 복사해 수정하지 않는다. 런타임이 없는 블로그는 Python을 준비하지 않는다. 런타임이 있는 제품은 자체 `doctor`와 사용자 자료를 쓰지 않는 `smoke`를 제공해야 하며, 경로·다운로드·해시 계약을 지킨다. 새 런타임 코드를 생성했다고 가정하지 않는다.

공통 정책·템플릿을 바꾸면 `references/projects.json`의 등록된 모든 저장소에 이 스킬과 설치기를 동기화한다. **한 제품만 수정한 채 둘 다 반영했다고 보고하지 않는다.** 다음 검사가 등록 프로젝트 누락과 템플릿·배포물 불일치를 거부한다.

```sh
python -B scripts/distribute.py check --repo VLOG_REPO --repo BLOG_REPO --require-all
```

새 프로젝트를 추가하면 registry도 추가하고 기존 프로젝트의 동작을 유지한다. 소스·설치기·문서·로컬 미러·최종 ZIP을 맞춘다. 기존 사용자 설치본은 설치 요청 없이 개발 배포 변경 때문에 덮어쓰지 않는다. 새 개인 지침도 자동 저장하지 않는다.

## 검증과 배포

게시 전 [배포 검사](references/release-gates.md)를 따른다. 검사에 통과한 **그 ZIP**을 게시하고 다운로드 SHA256을 다시 비교한다. `distribute.py package`는 파일 목록·템플릿·민감 자료 혼입·원본 일치를 검사한다. 이미 있는 산출물을 조용히 덮어쓰지 않는다.

GitHub의 `.github/workflows/installation.yml`은 두 OS × 두 클라이언트를 실제 OS에서 검사한다. `scripts/smoke_matrix.py`는 최종 ZIP의 프로젝트/사용자 설치·재실행·개인 지침·수정본 보존과 런타임 검사를 수행한다. 런타임 첫 설치는 빈 캐시와 제한된 PATH로 시작한다. CI 검사 도구용 Python을 제품 설치에 필요한 기존 Python으로 오인하지 않는다.

현재 세션의 설치·명령, 실제 이미지 열람 및 이후 명령, 새 채팅의 스킬 발견, 다른 계정 접근, 네이버 실계정 작업은 구분한다. CI에서 파일이 존재한다고 에이전트가 이미지나 스킬을 실제로 봤다고 보고하지 않는다. 자동 `agent_image_view: not_checked`는 보존하고 열람 증거는 별도 기록한다.

사용자가 이미 게시를 요청했다면 다시 승인 질문을 만들지 않고 검사·커밋·push·릴리스·다운로드 확인까지 진행한다. 게시 요청이 없는 작업은 검증된 결과를 준비하되 공개 게시를 추정하지 않는다. 실패한 검사를 숨기거나 검증이 끝나지 않은 조합을 성공으로 바꾸지 않는다.
