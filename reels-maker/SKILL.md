# 릴스 메이커

사용자는 영상 파일을 채팅에 직접 첨부하거나 영상 폴더를 지정하고 원하는 분위기를 말한다. 에이전트가 설치·장면 확인·편집·수정을 맡는다. 설치 명령이나 JSON 작성을 사용자에게 넘기지 않는다. 이 스킬은 로컬 편집 코드와 작업 지침이며 영상 내용을 자동 판정하는 별도 AI 모델이나 앱을 설치하지 않는다.

먼저 현재 대화의 작업 범위를 구분한다. **이 스킬의 소스·GitHub 배포본을 개발하는 대화에서는 기본값 변경과 “스킬 패치”를 배포 코드·문서·번들의 수정으로 처리한다. 개인 취향 저장 질문으로 바꾸지 않는다.** 개발 범위가 이미 확인됐다면 이후 기본값 수정 요청에도 유지한다. 일반 영상 제작 대화에서 편집 취향을 요청한 경우에는 아래 개인 오버라이드 흐름을 사용한다. 예시 문장을 실제 개인 지침으로 저장하지 않는다.

영상 제작 시 사용자가 승인한 개인 지침은 대화 밖에 보존한다. 작업 시작에 `overrides show`로 읽고, 이번 요청 > 개인 지침 > 스킬 기본값 순으로 적용한다. 재사용할 선호가 새로 나오면 **현재 영상에 반영한 뒤 구체적인 전·후 패치를 보여주고 “스킬의 개인 기본 지침에 반영할까요?”라고 제안**한다. 승인 전에는 저장하지 않는다. [개인 오버라이드 과정](references/user-overrides.md)을 읽고 적용하며, 저장된 개인 지침 파일은 스킬 업데이트·배포물과 분리한다.

작업 시작과 렌더 후에는 [타입별 제작 이력](references/production-history.md)을 따른다. 이력을 읽어 같은 타입의 제안을 개선하고, 렌더 후 작품·버전·실제 스타일을 누적하며 사용자 피드백으로 갱신한다. 렌더 성공을 만족으로 기록하거나 이력만으로 개인 기본값을 자동 변경하지 않는다.

이전 daily-vlog에서 이름을 바꾸었다. 기존 설치·개인 지침·작업 기록의 보존은 [이름 변경과 호환성](references/renaming.md)을 따른다.

## 첫 실행

설치와 첫 사용의 권한·도구 오류는 [설치와 실행 진단](references/installation.md)을 먼저 따른다. Codex와 로컬 Claude Code를 지원한다. 프로젝트 설치의 런타임은 같은 프로젝트 안에서 자동 선택되며, 설치 기록으로 해당 클라이언트의 개인 지침을 읽는다. `context` 또는 `doctor`의 `installation`에서 선택된 범위와 프로필 경로를 확인한다. 직접 호출은 Codex `$reels-maker`, Claude Code `/reels-maker`다. 파일 복사, 도구 준비, 테스트 영상 읽기, 에이전트의 이미지 열람을 구분하고, 명령 실행 자체가 실패하면 영상 내용이나 코덱 문제로 단정하지 않는다.

먼저 운영체제를 확인한다. macOS는 `bash scripts/run.sh doctor`, Windows x64는 `scripts\run.cmd doctor`를 스킬 경로 기준으로 실행한다. 아래 예제의 `bash scripts/run.sh`는 Windows에서 `scripts\run.cmd`로 바꿔 호출하고, 파일 경로는 사용자 환경의 절대경로로 전달한다. 준비된 캐시가 있으면 설치 쓰기 없이 재사용하며, 캐시가 없으면 런처가 필요한 도구를 자동 준비한다. `setup`은 재설치·환경 복구가 실제로 필요할 때만 사용한다. 단순히 새 채팅을 시작했다는 이유로 기존 캐시에 쓰기 권한을 다시 요청하지 않는다. 설치 요청이 이미 있으면 그대로 진행한다. 편집만 요청한 새 사용자에게는 첫 실행에 인터넷으로 전용 편집 도구를 준비한다는 점을 한 문장으로 알린 뒤 실행한다. 별도 비용은 이 도구에 없지만 사용하는 에이전트 서비스 요금과는 구분한다.

런처가 버전을 고정한 uv, Python 3.12, Pillow, PyAV, FFmpeg를 사용자 캐시에 준비하고 점검한다. Homebrew·sudo·시스템 Python·셸 프로필 변경이 필요 없다. 실행 권한/네트워크 승인이 뜨면 실제 필요한 범위를 설명한다. 승인 거절이나 다운로드 실패를 우회하지 말고 원인과 다음 조치를 짧게 알려준다. 사용자에게 패키지 이름을 고르게 하지 않는다.

대상은 macOS 14 이상과 Windows 10/11 x64다. macOS·Windows의 설치 경로와 영상 입출력은 GitHub의 네 OS/클라이언트 경로 검사로 확인한다. 실제 Codex·Claude Code 프런트엔드의 스킬 인식·이미지 열람·새 채팅은 OS 자동 검사와 구분하고 해당 배포의 검증 기록을 확인한다. Windows ARM/32비트와 Linux는 지원하지 않는다. Windows 실행기는 이번 PowerShell 프로세스에만 스크립트 실행을 허용하며 시스템 실행 정책은 바꾸지 않는다. 조직 정책·보안 프로그램이 차단하면 우회하지 말고 필요한 승인과 오류를 설명한다. 초기화·지원 범위·캐시 경로와 실패 처리 세부는 [환경 안내](references/setup.md)를 읽는다.

## 단계별 진행과 사용자 확인

기본 흐름은 **영상 받기 → 형식·선택적 레퍼런스 링크 → 영상별 최대 사용 길이 질문(기본 2초) → 타임로그일 때만 촬영시간 표시 여부 질문 → 영상 분석 → 사용자 맥락 입력 → 자막·그림 콘티 → 콘티 수정·확인 → 시안 제작 → 수정·완성**이다. 분석 뒤 바로 완성 영상을 만들지 않는다. [진행 방식](references/workflow.md)을 읽고 적용한다.

[형식 선택](references/formats.md)에서 타임로그·일상 모음·이야기형 릴스와 AI 추천 선택지를 먼저 설명하며, 참고하고 싶은 영상이 있으면 링크를 함께 받는다. 레퍼런스가 없어도 진행하며 이미 받은 링크는 다시 묻지 않는다. 링크의 확인과 접근 실패 처리는 [레퍼런스](references/reference-video.md)를 따른다. 시작 질문은 한 번에 하나씩 묻고, 이번 요청이나 승인된 개인 지침에서 이미 정해진 값은 다시 묻지 않는다. 형식·레퍼런스·길이와 해당되는 시간 설정이 정해지면 “영상을 먼저 분석하고 상황·보여주고 싶은 내용·원하는 방향을 받은 뒤 자막과 그림 콘티를 만든다”고 안내한다. 분석 요약 뒤 [사용자 맥락 입력](references/workflow.md)을 한 번에 받는다. 이미 알려준 맥락은 재사용하고 빠진 핵심만 묻는다. 새 질문을 했다면 답이나 명시적인 내용 구성 위임을 받기 전에는 자막·콘티를 확정하지 않는다. 기본 흐름에서 글 콘티 승인을 따로 기다리지 않으며 사용자가 글 콘티부터 요청한 경우에만 따른다.

선택한 최대 길이 안에서 원본별 핵심 동작을 고른다. 기본 2초는 추천값이며 답변 없이 확정하지 않는다. 짧은 원본은 그대로 쓰고 길이 맞추기용 반복·정지·배속은 임의로 넣지 않는다. 타임로그 요청이면 촬영 순서로 연결한다. 타임로그에서 시간 표시를 선택했거나 다른 형식에서도 사용자가 명시적으로 요청했고 실제 촬영시각이 확인된 컷에만 시간 자막을 사용하며, 끄면 콘티·영상 모두 생략한다. 타임로그 요청을 긴 원본 전체의 요약이나 모든 브이로그의 고정 스타일로 확대하지 않는다.

- 파일 접근을 확인하고 형식·선택적 레퍼런스·최대 길이를 받는다. 촬영시간 표시 질문은 타임로그에서만 한다. 일상 모음·이야기형에서는 묻지 않고 미지정 시간 표시는 끈다. 사용자가 명시적으로 정한 시간 표시와 기존 작품·개인 설정은 유지한다. 영상 분석 요약 뒤 사용자 맥락을 받고, 그 맥락으로 자막·그림 콘티를 만든 뒤 피드백을 기다린다. 시작 설정 동의를 영상 렌더 승인으로 확대하지 않는다.
- 분석과 기본 자막을 바탕으로 [그림 콘티](references/visual-storyboard.md)에 따라 현재 세션의 이미지 생성 도구로 장면별 그림·컷 번호·자막 자리·효과 메모가 있는 콘티를 생성한다. 실제 영상 프레임 합성 시트로 대체하지 않는다. 콘티를 보며 배치와 스타일을 수정하고 같은 승인을 반복하지 않는다. 이미지 생성 기능이 없는 환경에서는 미완료임을 알리고 프롬프트를 보존한다.
- 콘티와 스타일 모두 확인되기 전에는 시안 MP4를 렌더하지 않는다. 장면 순서만 확인한 답변을 아직 보여주지 않은 자막·스타일의 승인으로 처리하지 않는다. 그림 콘티에서 함께 보여준 장면·스타일은 한 번의 확인으로 진행한다.
- 작업 폴더의 `vlog-session.json`에 현재 단계·제안 버전·확인된 선택·대기 중인 질문을 기록한다. 이 파일은 에이전트가 관리하며 사용자에게 JSON 편집을 요구하지 않는다. 재개 시 미승인 단계를 먼저 이어간다.
- 사용자가 수정 방향을 주면 그 범위에서 수정해 새 버전을 만든다. 승인 범위의 글씨 크기·구도 같은 작은 수정마다 같은 질문을 반복하지 않는다. 주제·장면 구성 등 승인한 방향을 크게 바꾸면 해당 단계로 돌아가 확인한다.

## 단계 안에서 사용할 편집 도구

선택한 형식의 자막 비중을 [형식 안내](references/formats.md)에 맞춘다. 이야기형은 장면 분석 후 자막을 쓰기 전에 [이야기와 자막](references/narrative.md)을 읽고 사용자 맥락을 우선해 **이야기 한 줄 → 장면별 역할 → 연결되는 자막 문장**을 정하고 그림 콘티에서 함께 보여준다. 이야기 방향은 분석 후 입력받은 사용자 맥락을 우선한다. 사용자가 내용 구성까지 맡겼을 때 실제 장면에 근거한 관점 하나를 추천하며, 형식 추천 위임만으로 내용 전체를 맡겼다고 보지 않는다. 행동 라벨 나열에 머무르거나 영상에 없는 원인·속마음을 사실로 만들지 않는다. 시각 효과는 정한 이야기 역할을 표현한다.

제목 추가, 시간 위치 고정, 폰트·크기·색 변경, 기본 스타일 저장 요청에는 [커스터마이징](references/customization.md)을 읽고 `text_overlays`와 `customize` 도구를 사용한다. 사용자가 말로 요청하면 에이전트가 설정을 수정해 새 버전을 만든다. 제목·시간·문장은 따로 설정하며 “항상 가운데”처럼 고정한 위치는 얼굴 회피 자동 이동으로 덮어쓰지 않는다. 이번 영상 수정과 이후 기본값 저장을 구분하고, 구체적인 수정 요청을 다시 승인받지 않는다.

타임로그는 담백한 시간·행동, 일상 모음은 짧은 관찰·감상 중심으로 [형식별 기준](references/formats.md)을 적용한다. 이야기형의 기본 스타일은 [역할별 자막 연출](references/default-editing.md)을 따른다. 이야기형에서는 **본문은 흰색 Pretendard SemiBold, 반응은 노란 기울임 마루 부리 SemiBold와 어두운 외곽선, 제목·마무리는 분홍빛 글로우의 마루 부리, 선택한 촬영시간은 작은 SUIT SemiBold**로 역할을 나눈다. 제목·리액션·본문을 모든 컷에 함께 넣지 않고, 실제 장면의 감정과 구도에 맞춰 강조한다. 그림 콘티에 선택한 형식과 자막 역할·위치·등장 의도를 표시하고 실제 폰트·움직임은 영상에서 확인한다. 원음은 최종 영상에 유지하는 것이 기본이다. 기본 렌더러의 무음 입력 제한을 이유로 원음을 자동 삭제하지 않는다.

폰트 후보·배치 비교에는 [용도별 글꼴](references/typography.md)을 읽는다. 번들 폰트와 라이선스를 쓰며 기존 계획·이번 요청·개인 지침은 새 기본값으로 덮어쓰지 않는다. 기존 Noto Sans KR 중앙 타임로그 계획과 [호환 기본값](references/timelog-style.json)은 보존한다. 새 계획에는 선택한 역할별 폰트를 요소마다 명시해 구형 렌더러의 Noto 자동 기본값이 새 스타일을 덮어쓰지 않게 한다. 기울임·글로우·팝·전환·원음 합성은 현재 기본 render 명령의 기능이라고 오인하지 말고 [구현 범위와 검수](references/default-editing.md#구현-범위와-검수)에 따라 작업별로 구현·검증한다.

1. 채팅에 직접 첨부한 영상과 사용자가 지정한 영상 폴더를 모두 입력으로 받는다. 첨부 파일의 실제 접근 가능한 로컬 경로가 제공되면 `bash scripts/run.sh inspect --files FILE1 FILE2 ...`로 그 파일들만 확인한다. 첨부 파일이 있다는 이유로 다시 폴더를 만들게 하지 않는다. 첨부 저장소의 부모 폴더 전체를 훑지 않는다. 폴더를 지정했다면 `bash scripts/run.sh inspect FOLDER`를 사용한다. 파일명만 보이거나 파일에 접근할 수 없는 경우에만 해당 영상을 다시 첨부하거나 접근 가능한 폴더 경로를 알려 달라고 한다. 실제 첨부 수신 기능·크기 제한은 사용하는 앱에 따르며, 이 스킬이 새로운 업로드 서버를 제공한다고 말하지 않는다. 파일명/수정시각을 촬영시각으로 사용하지 않는다. 원음·HEVC/HDR·회전 정보를 확인하고 원본은 보존한다. 필요하면 현재 환경의 변환·합성 지원을 확인해 작업 복사본에서 처리하고, 원음은 최종 합성에 유지한다. 지원되지 않으면 미완료 항목을 설명하며 무음 결과로 몰래 대체하지 않는다.
2. 짧은 영상은 `bash scripts/run.sh frames FILE --output-dir NEW_DIR`로 대표 프레임을 보고 실제 행동과 인물을 확인한다. 긴 영상이나 원하는 구간을 찾는 요청에는 [긴 영상·큰 파일 안내](references/long-video.md)를 읽고 `survey`로 전체 간격 샘플 → 후보 구간의 촘촘한 샘플 순서로 확인한다. 큰 원본은 편집 컴퓨터의 파일 경로로 받아 첨부 제한을 피하며, 원격 컴퓨터와 휴대폰 사이의 원본 전달이 자동으로 된다고 약속하지 않는다. 중요한 구간은 추가 프레임·경계도 확인한다. 크롭으로 얼굴·행동을 자르지 말고 자막이 입·손을 가리지 않게 조정한다. 스틸 확인만으로 전체 움직임/청취 검수를 통과했다고 하지 않는다.
3. 분석과 사용자 맥락 입력을 마치고 장면·자막을 정하면 [그림 콘티](references/visual-storyboard.md)에 따라 이미지 생성으로 콘티를 그린다. 최종 편집 계획이나 실제 영상 프레임은 생성의 필수 입력이 아니다. 이미지를 확인하고 보여준 뒤 피드백을 반영한다. 확인된 의도를 [계획 형식](references/plan.md)에 맞춰 편집 계획으로 옮긴다. 실제 폰트·픽셀 배치 확인은 영상 시안에서 하고, 필요한 경우에만 [선택 미리보기](references/style-preview.md)를 사용한다. 이미지 생성만으로 사용자 승인이나 동작 검수가 끝났다고 하지 않는다. 장면 선택·순서·구도·짧은 행동 자막은 실제 영상에서 정한다. 의미 없는 반복으로 분량을 채우지 않는다. 개인 영상은 스톡 배지를 붙이지 않는다. 촬영시각을 모르면 시계 자막을 생략하고, 사용자가 연출 시각을 요청한 경우에만 예시라고 표시한다.
4. 그림 콘티 수정·확인이 끝나면 제작을 안내한다. 선택한 본편 최대 길이·시간 표시 여부와 승인한 콘티·스타일을 편집 계획에 대조한 뒤 `bash scripts/run.sh render PLAN --root WORKDIR --output outputs/vlog-v001.mp4 --poster outputs/poster-v001.jpg`로 렌더한다. 기존 파일은 보존하고 새 버전 이름을 사용한다. 같은 컴퓨터의 다른 렌더 작업과 공유 락이 지정돼 있으면 `--shared-lock EXISTING_LOCK`을 반드시 넘긴다. 공유 락 경로는 현재 작업 환경의 지침에서 확인한다. 공유 락은 rb로 읽어 잠금만 획득하며 내용 수정·삭제·강제 해제하지 않는다. 렌더는 순차 수행한다.
5. 출력 규격·전체 디코드·대표 자막·크롭·입력 해시 보존·컷 경계를 확인한다. 밝기·색감은 원본 느낌 보존이 기본이며, HDR→SDR 변환이 필요하면 [색상 보존 기준](references/default-editing.md#원음과-출력)에 따라 본편 합성 전 같은 장면의 표시를 대조한다. HDR 태그만 보고 일괄 톤매핑하거나 메타데이터 검사만으로 색상 검수를 통과시키지 않는다. 최종 원음을 원본의 선택 구간과 대조한다. BGM은 사용 범위가 확인된 별도 파일만 쓰며, 없어도 원음은 유지한다. 원본에 소리가 없거나 사용자가 무음을 요청한 경우에 무음으로 만든다. 음량 수치 확인과 직접 청취를 구분한다.

## 결과와 수정

MP4·표지 프레임·편집 계획·실행 보고를 로컬 링크로 보여준다. “글씨 키워줘”, “이 장면 줄여줘”는 계획을 수정해 새 버전으로 만든다. 설치/렌더/분석 시간을 구분하고 새 컴퓨터·모든 휴대폰 형식·한 번 요청으로 항상 완성된다고 확대하지 않는다. 채팅 첨부는 사용하는 앱이 제공한다. 이 스킬은 받은 파일을 별도 외부 서버에 추가 업로드하지 않는다. 에이전트가 프레임을 읽는 동작은 사용 중인 서비스의 데이터 처리에 따르므로 완전 오프라인 AI라고 표현하지 않는다. 공개 게시·외부 전송은 별도 사용자 요청에 따른다.
